# Lesson 06: House rules: read before you contribute

**Time:** 5 minute video · 30 minute exercise
**You'll need:** nothing new

Most first pull requests that get closed aren't closed because the code is
bad. They're closed because the contributor broke a house rule they never
read: no issue first, an unsigned CLA, a missing sign-off, or AI-written
code in a project that doesn't accept it.

Every project writes its rules down. This lesson is about finding them,
and the four that catch beginners out most.

## Where the rules live

| File | What it tells you |
|---|---|
| `CONTRIBUTING.md` (or `.github/CONTRIBUTING.md`, or a "developer guide" site) | How to set up, test, and submit. **The most important file. Read all of it.** |
| `CODE_OF_CONDUCT.md` | How people are expected to treat each other, and how to report problems. |
| `LICENSE` | The terms your contribution will be shared under. |
| `.github/PULL_REQUEST_TEMPLATE.md` | The questions your PR description must answer. Fill in every section. |
| `SECURITY.md` | How to report a security bug *privately*. Never in a public issue. |

Big projects often keep their rules on a website instead. CPython's is the
[Python Developer's Guide](https://devguide.python.org/). If the README
links to one, that's the CONTRIBUTING file.

## What to look for when you read CONTRIBUTING

1. **Do they want an issue first?** Many projects only accept PRs for issues
   that already exist and that a maintainer has agreed to. A surprise PR for
   a new feature is often closed unread.
2. **How do you claim an issue?** Some want a comment ("I'd like to work on
   this"), some assign issues, some say "don't ask, just open a PR".
3. **How to set up and run the tests.** You did this in Lesson 05; every
   project has its own commands.
4. **Style and commit messages.** Linters, `pre-commit`, a commit message
   format, a changelog entry.
5. **Legal: a CLA or a DCO sign-off.** See below.
6. **AI policy.** See below. This is new, it varies the most between
   projects, and it changes often.

## Rule 1: Contributor License Agreements (CLAs)

A **CLA** is a legal agreement between you and the project. It confirms
you have the right to contribute your code and lets the project use and
license it. You normally keep your copyright.

How you'll meet one: you open your first PR, and **a bot comments** asking
you to sign. Your PR can't be merged until you do.

**Example: CPython.** You must sign the Python Software Foundation's
Contributor License Agreement before your PR can be merged. A bot,
`python-cla-bot`, comments on your PR, and you sign through the link in that
comment. It checks the email address of **every commit's author**, and you
sign once per email address. Your commits must use the email you signed
with, so set up your noreply address (Lesson 03) *before* you sign.

**Before you sign anything:**

- Read it. It's a legal document.
- **If you have a job, check your employment contract.** Many employers own
  code you write, even in your free time. Some projects need a separate
  *corporate* CLA from your employer.
- Many company-run projects (Google's and Microsoft's, for example) have
  their own CLA.

## Rule 2: The DCO and `Signed-off-by`

Some projects use the **Developer Certificate of Origin** (DCO) instead of a
CLA. There's nothing to sign on a website. Instead, every commit carries a
line certifying the [four statements of the DCO](https://developercertificate.org/):
in short, that you wrote the code or have the right to submit it.

```text
Signed-off-by: Ada Lovelace <12345678+ada@users.noreply.github.com>
```

git adds it for you with `-s`:

```bash norun
git commit -s -m "Fix the typo in the install guide"
```

**Forgot?** Fix the last commit, or every commit on your branch, then
update your PR:

```bash norun
git commit --amend -s --no-edit
git rebase --signoff main
git push --force-with-lease
```

(Use the first line for one commit, the second for all of them.
`--force-with-lease` is needed because you rewrote commits you'd already
pushed. It refuses to overwrite anything you haven't seen.)

**Examples:** the Linux kernel requires a `Signed-off-by` line on every
patch. QEMU requires one too. Projects on GitHub often check it with a
**DCO** status check on your PR. And some projects, like curl, say plainly
that they don't use `Signed-off-by` at all. That's the point: read the
rules for *this* project.

## Rule 3: AI policies

Projects now take very different positions on code and text written with AI
tools like ChatGPT, Copilot or Claude. Here are real policies, as they stood
in November 2026. **Always read the current version: these change.**

### Some projects ban it

- **Gentoo**: on 14 April 2024 its Council voted to forbid contributions
  created with the help of natural-language AI tools.
- **NetBSD**: code generated by a large language model is presumed to be
  "tainted" and must not be committed without written approval from core.
- **QEMU**: asks contributors not to use AI content generators for patches,
  and declines contributions where AI use is known or suspected.

### Some allow it, with disclosure and a human responsible

- **LLVM**: you may use AI tools, but a human must stay in the loop: you
  must read and review all generated code or text before asking anyone to
  review it, and label tool use. The example label is an `Assisted-by`
  trailer in the commit message.
- **nixpkgs** (NixOS): a responsible person must be in the loop, non-trivial
  automation must be disclosed, and LLM-assisted commits need an
  `Assisted-by` trailer. LLM output is **not allowed** in PR descriptions,
  comments or commit message bodies: write those yourself. "Vibe coding"
  without review is not permitted.

### Some allow it, and you're responsible for the result

- **CPython**: you're responsible for your contribution whatever tools you
  used. Saying you used AI is appreciated but not required. Using AI to
  change or bypass tests just to make them pass is not acceptable.
  Maintainers can label PRs that don't follow the guidelines.
- **curl**: AI-assisted code is accepted if it meets every normal standard,
  including tests and docs. If you report a security problem, you **must**
  say you used AI and check the findings yourself.

### Rules that work everywhere

1. **Find the AI section before you start**, not after your PR is closed.
2. **No policy written down?** Ask in the issue, or disclose anyway.
3. **Write your own comments and PR descriptions.** Maintainers want to
   talk to *you*. Several projects ban AI-written discussion outright, and
   many maintainers who allow AI code still object to AI-written prose.
4. **Understand every line you submit.** If a reviewer asks "why did you do
   this?", "the AI did it" isn't an answer.
5. **Never submit a bug or security report an AI found without
   reproducing it yourself.** Unverified AI reports waste maintainers'
   time, and some projects ban people for it.
6. **Use the exact disclosure format the project shows** (a trailer, a PR
   checkbox, a sentence). Don't invent your own.

Lesson 12 is about using AI tools *well* when a project allows them.

## Rule 4: The code of conduct

The code of conduct covers issues, PRs, chat and anywhere else the project
meets. It usually comes down to: be kind, assume good intent, no
harassment. It also says **how to report** someone who breaks it. That
protects you too.

## Your pre-flight checklist

Copy this into your notes for every new project:

```text
Project: ______________________
[ ] Read CONTRIBUTING (and the developer guide, if any)
[ ] Issue first? Is my issue free, and how do I claim it?
[ ] CLA to sign? DCO sign-off (git commit -s)?
[ ] AI policy: banned / disclose / allowed? Disclosure format?
[ ] Setup and test commands
[ ] Linters, pre-commit, commit message format, changelog entry
[ ] PR template sections
[ ] Code of conduct, and how to report problems
```
